# 多角色控制系统重构计划

## 📋 项目背景

当前游戏机制是玩家控制单个球体进行游戏。现需要重构为**多角色队伍控制系统**，玩家在角色选择界面选择3个角色组成队伍，进入关卡后每回合从中选择进行操作，每个角色拥有独立的技能管理系统。

### 核心变更
- **从单角色 → 多角色队伍**（固定3个角色）
- **从自动控制 → 手动选择角色**（点击选中 + 滚轮蓄力 + 点击发射）
- **从全局技能 → 角色专属技能**（技能选择需指定归属角色）
- **从单一失败条件 → 队伍全灭失败**（所有角色死亡才失败）

---

## 🎯 需求确认

### 角色选择规则
- **数量**：固定3个角色
- **重复限制**：不允许选择重复的角色
- **选择顺序**：玩家自由选择3个不同角色，有明确的位置标识（1号位、2号位、3号位）

### 角色生成规则
- **生成区域**：使用类似 `EnemySpawner` 的 `SpawnRangeConfig` 定义固定生成区域
- **位置分配**：随机生成，确保角色间有最小安全距离
- **生成时机**：关卡开始时生成所有队伍角色

### 操作机制
- **取消自动蓄力**：不再自动进入蓄力状态
- **选择角色**：左键点击场景中的球体进行选中
- **蓄力操作**：选中后使用滚轮调节蓄力力度
- **发射操作**：蓄力后再次点击发射球体
- **切换角色**：蓄力为0时点击其他角色可切换选中
- **取消选中**：右键取消当前选中状态

### 技能系统
- **技能归属**：每个技能属于特定角色，独立管理
- **技能选择**：关卡结束后，生成3个技能选项，每个选项已预先分配给特定角色
- **选择方式**：三选一机制，每个选项显示"X号位角色 - 技能名称"
- **技能池**：从全技能池中随机选择，生成时随机指派给3个角色（1号位、2号位、3号位各一个）
- **技能通用性**：技能本身可能是通用技能，但在本次选择中已指派给特定角色

### 失败条件
- **队伍全灭**：所有3个角色死亡才判定游戏失败
- **角色复活**：暂不支持复活机制

### 碰撞规则
- **玩家球体间**：可以相互碰撞，按照物理规则处理
- **玩家与敌人**：保持现有碰撞逻辑

## 📦 核心模块设计

### 1. 数据层（Data Layer）

#### 1.1 TeamData - 队伍数据容器
**职责**：
- 管理3个角色的配置数据
- 追踪存活角色数量
- 提供队伍状态查询接口

**核心字段**：
- 角色列表（固定3个）
- 存活角色计数器
- 队伍状态标记

#### 1.2 CharacterInstance - 角色实例数据
**职责**：
- 存储单个角色的运行时数据
- 关联角色配置和场景实例
- 管理角色专属技能列表

**核心字段**：
- 角色唯一ID
- 角色配置引用（PlayerData）
- 当前血量
- 存活状态
- 技能列表
- 场景球体实例引用

#### 1.3 GameSession 改造
**新增职责**：
- 存储 TeamData 到 PlayerRuntimeData
- 跨场景保留所有角色状态
- 提供队伍数据访问接口

**改动点**：
- PlayerRuntimeData 添加 TeamData 字段
- 添加队伍相关的便捷访问方法

---

### 2. 选择层（Selection Layer）

#### 2.1 CharacterSelectionManager 改造
**新增职责**：
- 支持多选模式（最多3个）
- 检测重复选择
- 管理选择顺序

**改动点**：
- 从单选（PlayerData）改为多选（List<PlayerData>）
- 添加重复检测逻辑
- 添加选择顺序管理（1号位、2号位、3号位）
- 开始游戏时创建 TeamData 并传递给 GameSession

#### 2.2 CharacterSelectionUI 改造
**新增功能**：
- 显示已选角色列表
- 显示选择位置（1/2/3号位）
- 提供移除按钮
- 显示选择限制（最多3个，不可重复）

---

### 3. 生成层（Spawn Layer）

#### 3.1 PlayerSpawner（新增）
**职责**：
- 在关卡开始时生成所有队伍角色
- 管理生成位置分配
- 防止球体重叠

**核心功能**：
- 从 GameSession 读取 TeamData
- 使用 SpawnRangeConfig 定义生成区域
- 随机分配位置，确保最小安全距离
- 为每个角色实例化球体预制体
- 将场景实例引用回写到 CharacterInstance

**生成流程**：
```
1. 读取 GameSession.TeamData
2. 遍历3个角色配置
3. 为每个角色：
   - 获取随机位置（防重叠）
   - 实例化对应预制体
   - 设置 PlayerData
   - 保存实例引用
4. 返回生成的球体列表
```

#### 3.2 SpawnRangeConfig（复用）
**使用方式**：
- 在每个关卡配置玩家生成区域
- 支持矩形或圆形范围
- 提供随机位置获取接口

---

### 4. 控制层（Control Layer）

#### 4.1 BallSelectionManager（新增）
**核心职责**：
- 管理玩家对球体的选择
- 处理点击射线检测
- 管理当前选中状态
- 控制输入启用/禁用

**核心功能**：
- 点击选择球体（射线检测 + Layer过滤）
- 切换选中角色（蓄力为0时）
- 取消选中（右键）
- 发布选中/取消选中事件
- 启用/禁用被选中角色的输入

**状态管理**：
- 当前选中的角色引用
- 所有活跃球体列表
- 选择限制条件

#### 4.2 PlayerInputHandler 改造
**改动点**：
- 移除自动进入蓄力的逻辑
- 添加右键取消选中的输入检测
- 点击时区分：选择球体 / 发射操作
- 优先级调整：选择 > 发射 > 其他输入

**新输入处理流程**：
```
1. 检测左键点击
2. 如果当前未选中角色 OR 蓄力为0：
   - 尝试射线检测选择球体
3. 如果已选中且蓄力>阈值：
   - 执行发射
4. 检测右键点击：
   - 取消选中当前角色
5. 检测滚轮输入：
   - 调节蓄力力度（仅在已选中时）
```

#### 4.3 ChargeSystem 改造
**改动点**：
- 移除滚轮模式的自动开始蓄力
- 改为外部调用 `StartCharging()` 才开始
- 支持 `ResetCharge()` 用于取消选中时重置

---

### 5. 技能层（Skill Layer）

#### 5.1 SkillManager 改造
**核心改动**：
- 添加技能归属映射（skillID → characterID）
- 提供按角色查询技能的接口
- 添加技能到指定角色
- 触发器检查时过滤角色ID

**新增数据结构**：
- 技能归属映射表：Dictionary<string skillID, string characterID>
- 角色技能列表缓存

**新增接口**：
- `AddSkillToCharacter(characterID, skillConfig)`
- `GetCharacterSkills(characterID)`
- `RemoveCharacterSkills(characterID)`（角色死亡时）

#### 5.2 SkillSelectionManager 改造
**核心改动**：
- 技能选择时预先分配归属角色
- 从全技能池生成3个随机选项，每个选项随机指派给一个角色（1/2/3号位）
- 玩家选择后直接应用到预先指派的角色

**新选择流程**：
```
1. 关卡完成触发技能选择
2. 从全技能池随机选择3个技能
3. 为每个技能随机指派归属角色（确保3个选项分别对应1/2/3号位）
4. 显示技能选项，格式："[1号位] 技能A"、"[2号位] 技能B"、"[3号位] 技能C"
5. 玩家选择1个技能（三选一）
6. 直接将技能添加到预先指派的角色
```

**分配策略**：
- 每次生成3个技能选项时，随机决定哪个技能分配给哪个角色
- 确保每个角色位（1/2/3号位）各有一个选项
- 如果某个角色已死亡，该位置的选项标记为灰色或跳过

#### 5.3 SkillTrigger 全面改造
**核心改动**：
- 所有触发器添加角色ID过滤
- 检查触发事件是否来自技能归属的角色
- 不匹配则跳过触发

**改造重点**：
- `CollisionTrigger`：检查碰撞球体是否是归属角色
- `StoppedTrigger`：检查停止球体是否是归属角色
- `PhaseStartTrigger`：通过事件传递角色上下文
- 其他所有触发器同理

#### 5.4 SkillEffect 全面改造
**核心改动**：
- 所有效果执行时指定目标角色ID
- 属性修改器应用到对应角色的 PlayerStats
- 伤害效果作用于对应角色

**改造重点**：
- `AddModifierEffect`：将修改器添加到指定角色的 PlayerStats
- `DamageEffect`：伤害应用到指定角色
- `HealEffect`：治疗应用到指定角色

**改动点**：
- 从单选改为多选
- 显示已选角色列表

- 提供移除按钮

### 7. 战斗层（Combat Layer）

#### 7.1 PlayerBehavior 改造
**核心改动**：
- 伤害处理时需要角色ID参数
- 从 CharacterInstance 读取/更新血量
- 死亡判定改为角色级别

**改动点**：
- `TakeDamage()` 添加 characterID 参数
- 从 GameSession.TeamData 查找对应角色
- 更新对应角色的 currentHealth
- 死亡时调用 DeathManager

#### 7.2 PlayerAttackManager 改造
**核心改动**：
- 攻击事件发布时携带角色ID
- 碰撞检测时识别是哪个角色的球体

**改动点**：
- `ProcessBallStopped()` 添加角色ID识别
- GameEventBus 事件添加角色ID字段

#### 7.3 DeathManager（新增）
**职责**：
- 处理单个角色死亡
- 检查队伍全灭条件
- 触发游戏失败事件

**核心逻辑**：
```
1. 接收角色死亡通知
2. 标记角色为死亡状态
3. 禁用/隐藏球体
4. 从可选列表移除
5. 检查队伍存活数量
6. 如果全灭 → 发布游戏失败事件
```

## ⚠️ 风险评估与对策

### 高风险项

#### 1. 技能系统改造复杂度 ⚠️⚠️⚠️
**风险描述**：
- 所有现有技能（触发器、效果）都需要改造
- 技能数量多，测试工作量大
- 可能遗漏某些技能的改造

**对策**：
- 建立技能测试清单，逐个验证
- 优先改造常用技能，确保核心功能
- 增量测试，每改造一批技能就测试一次
- 保留旧代码备份，便于回滚

#### 2. 输入系统冲突 ⚠️⚠️
**风险描述**：
- 点击既要选择球体又要发射，优先级容易混乱
- 蓄力状态管理复杂，容易出现状态不一致

**对策**：
- 明确优先级：选择 > 发射 > 其他
- 详细的状态图和注释
- 充分的边界测试

#### 3. 事件系统传参改动 ⚠️⚠️
**风险描述**：
- GameEventBus 事件添加角色ID字段，影响范围大
- 可能遗漏某些事件监听者的更新

**对策**：
- 统一修改事件定义
- 使用编译器检查找出所有调用点
- 全局搜索事件使用位置

### 中风险项

#### 4. 多角色状态同步 ⚠️
**风险描述**：
- 3个球体的状态需要正确同步
- UI更新可能延迟或不一致

**对策**：
- 使用事件驱动更新UI
- 集中管理状态变更
- 添加状态变化日志

#### 5. 性能影响 ⚠️
**风险描述**：
- 3个球体同时运行，可能影响性能
- UI更新频率增加

**对策**：
- 使用对象池管理球体
- UI更新使用增量更新而非全量刷新
- 定期性能测试

### 低风险项

#### 6. 角色选择UI体验
**风险描述**：
- 多选UI可能不够直观
- 操作流程可能繁琐

**对策**：
- 迭代优化UI设计
- 添加明确的操作提示
- 收集测试反馈
