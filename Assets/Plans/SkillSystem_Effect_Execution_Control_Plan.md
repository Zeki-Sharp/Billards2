# 技能系统效果执行控制优化计划

## 问题背景

当前技能系统中的 `isApplied` 标记存在设计问题：
1. **概念混淆**：混合了"执行状态"和"执行权限"两个不同概念
2. **逻辑循环**：用执行结果来判断是否允许执行
3. **职责不清**：`isApplied` 既管状态又管权限，导致逻辑纠缠

## 核心问题分析

### AlwaysTrue 触发器场景
- **设计目的**：被动技能、状态标记技能
- **触发机制**：对所有事件都返回 true
- **风险**：如果没有防重复机制，会导致无限叠加
- **需求**：执行后自动禁用，防止重复执行

### 条件触发器场景
- **设计目的**：基于特定条件的技能
- **触发机制**：只在满足条件时触发，需要重置才能再次触发
- **需求**：由重置条件控制执行权限，由移除条件控制效果状态
- **问题**：当前 `isApplied` 标记阻止了合理的重复执行

## 解决方案设计

### 核心思路：引入双标记系统

**完全分离两个概念**：
- **`isApplied`**：效果是否已应用（状态标记）
- **`canExecute`**：是否允许执行效果（权限标记）

### 标记职责划分

#### isApplied（状态标记）
- **职责**：记录效果是否已经应用到玩家身上
- **控制方**：移除条件
- **生命周期**：从效果应用到效果移除

#### canExecute（权限标记）
- **职责**：决定是否允许执行效果
- **控制方**：重置条件 + AlwaysTrue 触发器特殊逻辑
- **生命周期**：从技能触发到重置条件满足

## 实施计划

### 阶段1：引入双标记系统

#### 1.1 修改 IEffect 接口
- 添加 `canExecute` 属性
- 添加 `SetCanExecute(bool canExecute)` 方法
- 保持现有接口不变，确保向后兼容

#### 1.2 修改 StatModifierEffect
- 添加 `canExecute` 字段
- 实现 `SetCanExecute` 方法
- 修改 `ExecuteEffect` 逻辑，使用 `canExecute` 判断是否允许执行

### 阶段2：实现执行控制逻辑

#### 2.1 AlwaysTrue 触发器逻辑
```csharp
// 检查 canExecute
if (!canExecute) return false;

// 执行效果
bool result = ExecuteEffectInternal(eventData);

// 执行后自动禁用
if (result) {
    isApplied = true;
    canExecute = false; // 防止重复执行
}
```

#### 2.2 条件触发器逻辑
```csharp
// 检查重置条件
if (resetCondition != null && resetCondition.ShouldReset(eventData)) {
    canExecute = true; // 重置条件满足，允许执行
}

// 检查 canExecute
if (!canExecute) return false;

// 执行效果
bool result = ExecuteEffectInternal(eventData);

// 执行后保持 canExecute 状态
if (result) {
    isApplied = true;
    // canExecute 保持不变，由重置条件控制
}
```

### 阶段3：集成移除条件逻辑

#### 3.1 移除条件处理
```csharp
// 检查移除条件
if (effectRemovalCondition != null && effectRemovalCondition.ShouldRemoveEffect(eventData)) {
    isApplied = false; // 移除效果状态
    // canExecute 不受影响，仍由重置条件控制
}
```

### 阶段4：测试与验证

#### 4.1 功能测试
- 测试 AlwaysTrue 触发器不会无限叠加
- 测试条件触发器在重置后可以重新执行
- 测试移除条件正确移除效果
- 测试重置条件正确控制执行权限

#### 4.2 回归测试
- 确保现有技能功能不受影响
- 验证各种技能配置组合的正确性

## 架构优势

### 1. 概念清晰
- **isApplied**：只管效果状态
- **canExecute**：只管执行权限
- 两个概念完全独立，不会产生混淆

### 2. 逻辑简单
- AlwaysTrue：执行后自动禁用
- 条件触发器：由重置条件控制权限
- 移除条件：只管效果移除

### 3. 职责明确
- **重置条件**：控制 `canExecute`
- **移除条件**：控制 `isApplied`
- **触发器类型**：决定执行策略

### 4. 扩展性好
- 未来可以支持更复杂的执行控制逻辑
- 可以为不同的触发器类型定义不同的策略
- 易于添加新的效果类型

## 实施风险与缓解

### 风险1：接口变更影响
- **缓解**：通过扩展而非修改的方式，保持向后兼容

### 风险2：逻辑复杂度增加
- **缓解**：双标记系统逻辑简单明确，比之前的复杂判断更易理解

### 风险3：测试覆盖不足
- **缓解**：分阶段实施，每个阶段都有对应的测试计划

## 预期效果

### 1. 解决核心问题
- AlwaysTrue 触发器不会无限叠加
- 条件触发器可以正确控制执行权限
- 移除条件正确控制效果状态
- 重置条件正确控制执行权限

### 2. 提升系统灵活性
- 支持更复杂的技能设计需求
- 为未来的技能扩展提供更好的基础

### 3. 改善开发体验
- 技能配置更加直观
- 减少因设计限制导致的工作量
- 代码逻辑更清晰，易于维护

## 总结

本计划旨在通过引入双标记系统，彻底解决技能系统中效果执行控制的设计问题。通过完全分离"执行状态"和"执行权限"两个概念，实现清晰、简单、可维护的执行控制逻辑。
