# 值比较条件持续监控重新设计方案

## 问题描述

当前的值比较条件监控机制本身是合理的（初始化触发 + 值变化触发），但存在以下问题：
1. **缺乏状态变化检测**：条件不知道状态是否发生了变化
2. **缺乏状态记忆**：无法记住上一次的条件状态
3. **效果管理不足**：无法根据条件状态动态应用/移除效果

**需求**：实现持续监控技能系统
- 当Health = 1时：应用效果
- 当Health ≠ 1时：立即移除效果  
- 当Health重新 = 1时：重新应用效果

**核心问题**：现有机制可以检测到值变化，但无法区分"状态保持"和"状态变化"，导致效果无法动态管理。

## 当前系统分析

### 现有监控机制（已经足够好）
- **DataSourceTrigger**：✅ 初始化时触发一次，✅ Health变化时触发
- **监控机制**：✅ 能够检测到数据源的所有变化

### 真正的问题所在
- **ValueComparisonCondition**：❌ 缺乏状态记忆，每次都是独立检查
- **StatModifierEffect**：❌ 只能应用一次，无法根据状态变化动态移除
- **状态管理**：❌ 无法区分"状态保持"和"状态变化"
- **重复状态管理**：❌ 主条件和移除条件可能重复管理同一状态

### 具体场景分析
```
时间轴：Health: 0.8 → 1.0 → 0.9 → 1.0

当前机制：
1. 初始化：Health=0.8，条件不满足，不执行效果 ✅
2. 变化1：Health=1.0，条件满足，执行效果 ✅
3. 变化2：Health=0.9，条件不满足，但效果已经应用，无法移除 ❌
4. 变化3：Health=1.0，条件满足，但效果已应用，不会重复执行 ✅

结果：当Health从1.0变为0.9时，攻击力加成效果仍然存在，这是不对的！

重复状态管理问题：
- 主条件：ValueComparisonCondition.CheckCondition() 管理状态
- 移除条件：InverseConditionCheckEffectRemovalCondition.ShouldRemoveEffect() 
  内部又调用 originalCondition.CheckCondition() 再次管理状态
- 结果：同一状态被重复管理，可能导致不一致
```

### 技能执行流程
```
数据变化 → 触发器检测 → 条件检查 → 执行效果 → 重置条件
```

**问题**：条件检查只是简单的"当前值比较"，缺乏"状态变化检测"。

## 重新设计方案

### 设计原则
**保持现有监控机制不变**，只改进状态管理和效果生命周期管理。

### 1. 触发器（Trigger）保持现状 ✅

#### 现有机制已经足够好
- `DataSourceTrigger`：✅ 初始化时触发一次，✅ Health变化时触发
- **无需修改**：现有的监控机制已经能够检测到所有数据变化

#### 关键特性（保持不变）
- ✅ 初始化时检查一次
- ✅ 值变化时触发事件
- ✅ 专注于数据变化的检测

### 2. 条件（Condition）增强设计

#### 当前问题
- `ValueComparisonCondition`只是简单的值比较
- ❌ 不支持状态记忆
- ❌ 无法区分"状态保持"和"状态变化"

#### 增强设计：为现有ValueComparisonCondition添加状态记忆
```csharp
public class ValueComparisonCondition : ICondition
{
    // 现有字段保持不变...
    private ComparisonType comparisonType = ComparisonType.GreaterThanOrEqual;
    private float targetValue = 1.0f;
    private System.Func<object, float> valueExtractor;
    
    // 新增：状态记忆字段
    private bool lastConditionState = false;
    private bool hasInitialized = false;
    
    public bool CheckCondition(object eventData)
    {
        if (valueExtractor == null)
        {
            Debug.LogWarning($"[{ConditionName}] 值提取器未设置");
            return false;
        }
        
        float currentValue = valueExtractor(eventData);
        bool currentState = PerformComparison(currentValue);
        
        // 初始化时总是检查
        if (!hasInitialized)
        {
            hasInitialized = true;
            lastConditionState = currentState;
            Debug.Log($"[{ConditionName}] 初始化检查: {currentValue} vs {targetValue} = {currentState}");
            return currentState;
        }
        
        // 状态变化时才返回true
        if (currentState != lastConditionState)
        {
            lastConditionState = currentState;
            Debug.Log($"[{ConditionName}] 状态变化: {currentValue} vs {targetValue} = {currentState}");
            return true; // 状态变化，需要处理
        }
        
        return false; // 状态未变化，不需要处理
    }
    
    // 新增：获取当前状态（不改变状态记忆）
    public bool GetCurrentState(object eventData)
    {
        if (valueExtractor == null) return false;
        float currentValue = valueExtractor(eventData);
        return PerformComparison(currentValue);
    }
    
    // 新增：获取上次状态
    public bool GetLastState()
    {
        return lastConditionState;
    }
    
    private bool PerformComparison(float currentValue)
    {
        switch (comparisonType)
        {
            case ComparisonType.GreaterThanOrEqual:
                return currentValue >= targetValue;
            case ComparisonType.LessThanOrEqual:
                return currentValue <= targetValue;
            case ComparisonType.Equal:
                return Mathf.Approximately(currentValue, targetValue);
            case ComparisonType.InRange:
                return currentValue >= minValue && currentValue <= maxValue;
            default:
                return false;
        }
    }
}
```

#### 关键特性
- ✅ **保持现有接口和功能不变**
- ✅ **新增状态记忆能力**：记录上一次的条件状态
- ✅ **只在状态发生变化时返回true**：避免重复处理
- ✅ **提供状态查询接口**：GetCurrentState() 和 GetLastState()
- ✅ **初始化时总是检查一次**：确保初始状态正确

### 3. 效果（Effect）增强设计

#### 当前问题
- `StatModifierEffect`只能应用一次
- ❌ 不支持动态移除和重新应用
- ❌ 缺乏状态管理

#### 增强设计：为现有StatModifierEffect添加移除检查
```csharp
public class StatModifierEffect : IEffect
{
    // 现有字段保持不变...
    private string targetStat = "Damage";
    private float modifierValue = 1.5f;
    private PlayerCore targetPlayer;
    private PlayerStatsManager statsManager;
    private StatModifier appliedModifier;
    private IEffectRemovalCondition effectRemovalCondition;
    
    // 新增：状态管理
    private bool effectCurrentlyActive = false;
    
    public bool ExecuteEffect(object eventData)
    {
        if (targetPlayer == null || statsManager == null)
        {
            Debug.LogError($"[{EffectName}] 目标玩家或属性管理器为空，无法执行效果");
            return false;
        }
        
        // 首先检查是否需要移除效果
        if (effectRemovalCondition != null && effectRemovalCondition.ShouldRemoveEffect(eventData))
        {
            if (effectCurrentlyActive)
            {
                RemoveEffect();
                effectCurrentlyActive = false;
                Debug.Log($"[{EffectName}] 移除效果: {targetStat}");
                return true;
            }
        }
        
        // 如果效果未激活，则应用效果
        if (!effectCurrentlyActive)
        {
            ApplyEffect();
            effectCurrentlyActive = true;
            Debug.Log($"[{EffectName}] 应用效果: {targetStat} x{modifierValue}");
            return true;
        }
        
        return false; // 状态未变化，无需处理
    }
    
    private void ApplyEffect()
    {
        // 创建修饰器
        appliedModifier = new StatModifier(
            targetStat,
            StatModifierType.PercentAdd,
            modifierValue - 1f,
            this
        );
        
        // 应用修饰器
        statsManager.ApplyModifier(appliedModifier);
        
        // 触发表现效果
        TriggerVisualEffect();
    }
    
    private void RemoveEffect()
    {
        // 移除修饰器
        if (appliedModifier != null && statsManager != null)
        {
            statsManager.RemoveModifier(appliedModifier);
            Debug.Log($"[{EffectName}] 移除修饰器: {appliedModifier.GetDebugInfo()}");
            appliedModifier = null;
        }
    }
}
```

#### 关键特性
- ✅ **职责清晰**：Effect专注于执行，移除条件专注于判断
- ✅ **保持现有接口**：不破坏现有功能
- ✅ **支持动态管理**：根据移除条件动态应用/移除效果
- ✅ **避免重复操作**：通过状态标志避免重复应用和移除

### 4. 效果移除（Effect Removal）增强设计

#### 当前问题
- 现有的效果移除机制不适合持续监控需求
- 主要通过时间或回合结束移除
- 缺乏基于条件状态的动态移除

#### 增强设计：利用现有的 InverseConditionCheck
对于持续监控技能，使用现有的 `EffectRemovalType.InverseConditionCheck` 类型：
- **保持现有架构不变**
- **增强 InverseConditionCheckEffectRemovalCondition 的状态记忆能力**
- **让移除条件专注于判断，Effect专注于执行**

#### 增强的 InverseConditionCheckEffectRemovalCondition
```csharp
public class InverseConditionCheckEffectRemovalCondition : IEffectRemovalCondition
{
    private ICondition originalCondition;
    
    public bool ShouldRemoveEffect(object eventData)
    {
        if (originalCondition == null)
        {
            Debug.LogWarning($"[{ConditionName}] 原始条件未设置");
            return false;
        }
        
        // 使用原始条件的当前状态，避免重复状态管理
        bool currentConditionMet = originalCondition.GetCurrentState(eventData);
        bool lastConditionMet = originalCondition.GetLastState();
        
        // 只在状态变化时检查移除
        if (currentConditionMet != lastConditionMet)
        {
            return !currentConditionMet; // 条件变为false时移除
        }
        
        return false; // 状态未变化，不移除
    }
}
```

#### 关键特性
- ✅ **职责清晰**：移除条件专注于判断，Effect专注于执行
- ✅ **利用现有架构**：使用现有的 InverseConditionCheck 类型
- ✅ **避免重复状态管理**：使用原始条件的状态信息，不重复管理
- ✅ **配置一致**：保持现有配置接口不变

## 新的技能执行流程

### 持续监控模式流程
```
数据变化 → DataSource触发器检测 → 状态变化条件检查 → 移除条件检查 → 效果管理
    ↓
移除条件返回true → 移除效果
    ↓
移除条件返回false → 应用效果（如果未应用）
    ↓
状态重新变化 → 重新检查移除条件
```

### 与传统模式对比

| 方面 | 传统模式 | 持续监控模式 |
|------|----------|--------------|
| 触发器 | 一次性触发 | ✅ 数据变化时触发（已有） |
| 条件检查 | 简单值比较 | ✅ 状态变化检查（增强） |
| 效果管理 | 应用一次 | ✅ 动态应用/移除（增强） |
| 重置机制 | 需要重置 | ✅ 无需重置（简化） |
| 配置复杂度 | 中等 | ✅ 简化（减少移除配置） |
| 适用场景 | 一次性技能 | ✅ 持续状态技能 |

## 总结

基于你的正确观察和架构分析，现有监控机制（初始化触发 + 值变化触发）已经足够好了。真正需要改进的是**状态管理和职责分离**：

### 关键改进点
1. **ValueComparisonCondition**：添加状态记忆，只在状态变化时返回true
2. **InverseConditionCheckEffectRemovalCondition**：增强状态记忆，实现智能移除判断
3. **StatModifierEffect**：添加移除检查逻辑，保持职责分离
4. **配置一致性**：使用现有的InverseConditionCheck类型

### 设计优势
- ✅ **职责清晰**：移除条件专注于判断，Effect专注于执行
- ✅ **架构一致**：利用现有的EffectRemovalConfig体系
- ✅ **向后兼容**：不影响现有技能的功能
- ✅ **可扩展性强**：支持复杂的移除场景
- ✅ **状态驱动**：实现真正的状态驱动效果管理

### 核心架构原则
- **单一职责原则**：每个组件专注于自己的职责
- **开闭原则**：对扩展开放，对修改封闭
- **依赖倒置原则**：依赖抽象而非具体实现

通过这种方式，可以在**保持现有监控机制和架构**的基础上，实现你需要的持续监控功能："Health=1时应用效果，Health≠1时移除效果，Health重新=1时重新应用效果"。
