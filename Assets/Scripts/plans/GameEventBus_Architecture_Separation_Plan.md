# GameEventBus 架构分离重构计划

## 问题分析

### 当前架构问题
- **职责混乱**：`PublishAttack` 和 `PublishDeath` 同时处理游戏逻辑和表现逻辑
- **层次混乱**：表现系统逻辑被嵌入到游戏逻辑层
- **扩展性差**：新增表现效果需要修改发布方法
- **测试困难**：无法独立测试游戏逻辑，表现逻辑难以隔离
- **数据结构冗余**：`AttackData` 和 `AttackEffectEvent` 字段完全相同，职责重复
- **维护成本高**：两套结构体需要同步维护，修改需要更新多处

### 核心问题
1. 表现事件不应该在发布方法中直接调用，而应该由表现系统独立响应游戏事件
2. 重复的数据结构定义增加了维护成本和内存开销
3. 无意义的数据转换逻辑降低了系统效率

## 重构目标

### 架构目标
- **职责分离**：游戏逻辑与表现逻辑完全解耦
- **层次清晰**：游戏逻辑层 → 事件总线 → 表现层
- **扩展性强**：表现系统可独立扩展，不影响游戏逻辑
- **测试友好**：游戏逻辑可独立测试
- **结构简化**：统一数据结构，消除冗余定义
- **维护优化**：减少重复代码，降低维护成本

### 设计原则
- **单一职责**：每个发布方法只处理对应的事件逻辑
- **事件驱动**：表现系统通过订阅事件响应
- **分层架构**：保持游戏逻辑层和表现层的独立性
- **数据结构统一**：游戏逻辑和表现层共用相同的数据结构
- **最小冗余**：避免重复定义相同的数据结构

## 重构策略

### 阶段1：数据结构统一
- **目标**：合并重复的数据结构定义
- **范围**：`AttackData`、`AttackEffectEvent`、`DeathData`、`DeathEffectEvent`
- **原则**：保留逻辑层结构，删除表现层重复结构

### 阶段2：简化发布方法
- **目标**：移除发布方法中的表现逻辑和数据转换
- **范围**：`PublishAttack` 和 `PublishDeath` 方法
- **原则**：只保留游戏逻辑事件触发

### 阶段3：表现系统重构
- **目标**：让表现系统独立响应游戏事件
- **范围**：`EffectManager` 和相关表现组件
- **原则**：通过事件订阅响应游戏逻辑，直接使用统一数据结构

### 阶段4：架构验证
- **目标**：验证新架构的正确性
- **范围**：全系统集成测试
- **原则**：确保功能完整性和性能

## 实施步骤

### 步骤1：数据结构分析与统一
- 分析 `AttackData` 与 `AttackEffectEvent` 的字段差异
- 分析 `DeathData` 与 `DeathEffectEvent` 的字段差异
- 确定统一后的数据结构定义
- 删除重复的结构体定义

### 步骤2：发布方法重构
- 移除 `PublishAttack` 中的表现逻辑和数据转换
- 移除 `PublishDeath` 中的表现逻辑和数据转换
- 保持方法签名不变，确保兼容性
- 简化发布方法，只触发游戏逻辑事件

### 步骤3：表现系统重构
- 修改 `EffectManager` 订阅游戏逻辑事件
- 更新 `MMEventManager` 调用，直接使用统一数据结构
- 移除数据转换逻辑
- 确保表现系统的正确响应

### 步骤4：系统集成与测试
- 测试攻击事件的完整流程
- 测试死亡事件的完整流程
- 验证表现效果的正确性
- 验证数据结构的统一性

### 步骤5：清理与优化
- 清理无用的数据结构定义
- 更新相关文档和注释
- 优化事件系统的性能

## 风险评估

### 技术风险
- **兼容性风险**：现有调用代码可能需要调整
- **性能风险**：事件订阅可能影响性能
- **集成风险**：表现系统响应时机可能不当

### 缓解措施
- **渐进式重构**：分阶段实施，降低风险
- **充分测试**：每个阶段都进行完整测试
- **回滚准备**：保留原有代码作为备份
