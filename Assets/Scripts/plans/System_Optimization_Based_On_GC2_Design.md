# 基于 Game Creator 2 设计思路的系统优化清单

## 文档信息
- **创建日期**: 2024年12月
- **版本**: 1.0
- **状态**: 规划阶段
- **目标**: 借鉴 GC2 的优秀设计模式优化现有系统

---

## 概述

本文档总结了通过分析 Game Creator 2 插件后，发现的8个可以应用到我们项目中的优秀设计模式。这些优化方向不会改变现有系统的核心架构，而是通过引入更好的设计模式来提升代码质量、可维护性和扩展性。

**核心原则**：
- ✅ 保持现有系统的核心优势
- ✅ 借鉴设计思路，不照搬代码
- ✅ 分阶段实施，充分测试
- ✅ 提升开发效率和可维护性

---

## 优化项清单

### 1. 配置系统多态化 ⭐⭐⭐⭐⭐

**优先级**: 最高  
**难度**: 中等  
**收益**: 极高  
**推荐指数**: ⭐⭐⭐⭐⭐

#### 当前问题
- 使用 `enum + switch` 模式创建实例
- 所有类型的参数混在同一个配置类中
- 需要使用 `ShowIf` 隐藏不相关参数
- 新增类型需要修改多处代码
- Inspector 显示冗余字段

#### GC2 的设计思路
- 使用 `SerializeReference` 实现多态序列化
- 每个类型只包含自己的参数
- 通过抽象基类统一接口
- 使用类型选择器动态选择实现

#### 优化方向
- **TriggerConfig 多态化**
  - 创建 `TriggerBase` 抽象类
  - 每个触发器继承基类，只包含自己的参数
  - 使用 `[SerializeReference]` 和 `[TypeSelector]`

- **ConditionConfig 多态化**
  - 创建 `ConditionBase` 抽象类
  - 简化复合条件的配置方式
  - 每个条件独立配置

- **EffectConfig 多态化**
  - 创建 `EffectBase` 抽象类
  - 效果参数完全独立
  - 支持效果嵌套和组合

#### 预期收益
- ✅ Inspector 体验显著提升（只显示相关参数）
- ✅ 代码扩展性极大增强（符合开闭原则）
- ✅ 类型安全性提升（编译时检查）
- ✅ 减少配置错误（无冗余参数）

#### 实施建议
1. 先创建抽象基类
2. 逐步迁移现有实现类
3. 编写数据迁移工具
4. 充分测试后替换旧系统

### 2. Args 参数传递系统 ⭐⭐⭐⭐

**优先级**: 高  
**难度**: 低  
**收益**: 高  
**推荐指数**: ⭐⭐⭐⭐

#### 当前问题
- 直接传递 `object` 类型的事件数据
- 每次都需要类型转换
- 无类型安全保障
- 重复的 GetComponent 调用

#### GC2 的设计思路
- 统一的 `Args` 参数容器
- 包含事件发起者和目标对象
- 内置组件缓存机制
- 提供类型安全的访问方法

#### 优化方向
- 创建 `SkillArgs` 统一参数类
  - 包含 Source 和 Target 对象
  - 支持多种事件数据（AttackData, DeathData 等）
  - 内置组件缓存，避免重复查找
  - 提供类型安全的访问接口

- 统一所有接口签名
  - ITrigger.CheckEvent(SkillArgs args)
  - ICondition.CheckCondition(SkillArgs args)
  - IEffect.ExecuteEffect(SkillArgs args)

#### 预期收益
- ✅ 类型安全（无需手动类型转换）
- ✅ 性能提升（组件缓存）
- ✅ 代码可读性增强
- ✅ 更好的 IDE 支持

#### 实施建议
1. 创建 SkillArgs 类
2. 更新所有接口定义
3. 逐步迁移现有实现
4. 保留兼容适配器（过渡期）

### 3. Property 动态值系统 ⭐⭐⭐⭐

**优先级**: 高  
**难度**: 中等  
**收益**: 高  
**推荐指数**: ⭐⭐⭐⭐

#### 当前问题
- 技能配置中只能使用固定值
- 无法配置动态计算的值
- 缺少灵活性

#### GC2 的设计思路
- Property 系统支持多种值来源
- 可以是固定值、变量、随机数、计算结果
- 运行时动态获取
- 支持复杂的值表达式

#### 优化方向
- 创建 `DynamicFloat` / `DynamicInt` 等动态值类型
- 支持多种值提供者：
  - 固定值
  - 随机范围
  - 基于血量百分比
  - 基于技能等级
  - 从变量读取
  - 数学表达式计算

#### 预期收益
- ✅ 技能配置更灵活
- ✅ 支持更复杂的机制
- ✅ 减少硬编码
- ✅ 易于平衡调整

#### 应用场景
- 伤害倍率随血量变化
- 技能范围随等级增长
- 随机效果数值
- 基于玩家属性的计算

#### 实施建议
1. 先实现 DynamicFloat 基础框架
2. 添加常用的值提供者
3. 在技能配置中逐步替换固定值
4. 根据需要扩展更多提供者

### 5. Manager 单例模式统一 ⭐⭐⭐

**优先级**: 中  
**难度**: 低  
**收益**: 中  
**推荐指数**: ⭐⭐⭐

#### 当前问题
- 每个 Manager 都重复实现单例逻辑
- 代码冗余
- 容易出错（忘记 DontDestroyOnLoad 等）

#### GC2 的设计思路
- 使用泛型基类 `Singleton<T>`
- 统一的生命周期管理
- 提供 OnCreate/OnDestroy 虚方法
- 处理应用退出情况

#### 优化方向
- 创建 `SingletonManager<T>` 基类
- 所有 Manager 继承该基类
- 统一处理：
  - 实例创建和销毁
  - DontDestroyOnLoad
  - 重复实例检测
  - 应用退出处理

#### 预期收益
- ✅ 消除代码重复
- ✅ 统一的生命周期管理
- ✅ 减少出错可能
- ✅ 更清晰的 Manager 结构

#### 适用范围
- SkillManager
- WeakPointManager
- EffectManager
- 所有全局单例管理器

#### 实施建议
1. 创建 SingletonManager<T> 基类
2. 从最简单的 Manager 开始迁移
3. 测试确保行为一致
4. 逐步迁移所有 Manager

### 6. 事件系统优先级增强 ⭐⭐⭐

**优先级**: 中  
**难度**: 低  
**收益**: 中  
**推荐指数**: ⭐⭐⭐

#### 当前状态
- 已定义 EventPriority 枚举
- IDamageModifier 已使用优先级
- GameEventBus 未使用优先级排序

#### GC2 的设计思路
- 事件订阅者可以指定优先级
- 按优先级顺序执行回调
- 高优先级可以拦截或修改事件

#### 优化方向
- 创建 `PriorityEventManager<T>` 类
- 为每个事件维护优先级订阅列表
- 订阅时可指定：
  - 优先级等级
  - 订阅者名称（调试用）
- 发布时按优先级顺序执行

#### 预期收益
- ✅ 确保关键逻辑优先执行
- ✅ 更可控的事件处理流程
- ✅ 便于调试（知道执行顺序）
- ✅ 支持事件拦截机制

#### 应用场景
- 伤害计算流程
- 技能触发顺序
- 状态效果应用
- UI 更新时机

#### 实施建议
1. 创建 PriorityEventManager 类
2. 在新事件中试用
3. 确认效果后扩展到所有事件
4. 为关键事件标注优先级需求

### 9. Data/Info 分离模式 ⭐⭐⭐⭐

**优先级**: 高  
**难度**: 低  
**收益**: 高  
**推荐指数**: ⭐⭐⭐⭐

#### 当前问题
- 数据和显示信息混在一起
- EnemyData 同时包含战斗数值和UI显示
- PlayerData 同时存储属性和描述文本
- 难以动态修改显示内容

#### GC2 的设计思路（来自 Stats 系统）
- **Data 类**：只包含核心数据（数值、引用、配置）
- **Info 类**：只包含显示信息（名称、图标、描述、颜色）
- 使用 `PropertyGetString`、`PropertyGetSprite` 支持动态获取
- 通过 `TInfo` 抽象基类统一接口

#### 优化方向
- 为 EnemyData 创建独立的 EnemyInfo
  - 名称、图标、描述文本分离
  - 支持多语言（通过 Property 系统）
  - 可配置颜色标识
  
- 为 SkillConfig 创建独立的 SkillInfo
  - 技能名称和图标独立配置
  - 支持动态描述生成（显示实际数值）
  - 统一的显示接口

- 创建 `TInfo` 基类统一所有显示信息
  - Name、Acronym、Description、Icon、Color
  - 提供 `GetName(Args)` 等标准方法
  - 便于UI系统统一处理

#### 预期收益
- ✅ 配置结构更清晰（数据/显示分离）
- ✅ 支持动态显示内容（基于游戏状态）
- ✅ 便于实现多语言系统
- ✅ UI系统接口统一

#### 应用场景
- 敌人信息显示
- 技能卡片UI
- 物品信息面板
- 角色属性界面

#### 实施建议
1. 创建 TInfo 抽象基类
2. 为现有配置添加 Info 字段
3. 逐步将显示相关字段迁移到 Info
4. 更新 UI 系统使用统一接口

### 10. Class/Instance 分离模式 ⭐⭐⭐⭐⭐

**优先级**: 最高  
**难度**: 中  
**收益**: 极高  
**推荐指数**: ⭐⭐⭐⭐⭐

#### 当前问题
- PlayerData 和 EnemyData 直接在运行时修改
- 无法区分基础配置和运行时状态
- 难以重置到初始状态
- 实例化后配置共享问题

#### GC2 的设计思路（来自 Stats 系统）
- **Class（配置层）**：ScriptableObject，定义模板
  - 包含 AttributeList、StatList 等配置
  - 不可变，作为共享数据源
  
- **Traits（实例层）**：MonoBehaviour，运行时实例
  - 引用 Class 作为配置源
  - RuntimeStats、RuntimeAttributes 管理运行时状态
  - 支持 Override 覆盖默认值
  
- **Override 机制**：
  - OverrideAttributes、OverrideStats
  - 允许在实例层面微调初始值
  - 不影响原始配置

#### 优化方向
- **角色系统重构**
  - PlayerData（配置） → PlayerClass（模板配置）
  - 新增 PlayerStats（运行时组件）
  - 新增 PlayerOverride（实例覆盖配置）
  
- **敌人系统重构**
  - EnemyData（配置） → EnemyClass（模板配置）
  - 新增 EnemyStats（运行时组件）
  - 支持同一模板生成不同强度的敌人实例
  
- **技能系统增强**
  - SkillConfig 保持不变（已是配置）
  - SkillInstance 已分离（已实现运行时实例）
  - 可参考 Override 模式支持技能定制

#### 预期收益
- ✅ 配置和状态完全分离（架构清晰）
- ✅ 支持配置复用（多实例共享配置）
- ✅ 易于重置和调试（基于模板重建）
- ✅ 支持敌人等级变化（基于同一模板）
- ✅ 符合数据驱动设计原则

#### 应用场景
- 同一敌人类型的多个实例
- 玩家角色多次重生
- 技能效果的实例化
- 配置热重载

#### 实施建议
1. 创建 PlayerClass 和 PlayerStats
2. 创建 EnemyClass 和 EnemyStats
3. 添加 Override 配置支持
4. 迁移现有数据到新结构
5. 更新实例化逻辑

### 11. 三层属性系统设计 ⭐⭐⭐⭐

**优先级**: 高  
**难度**: 中  
**收益**: 高  
**推荐指数**: ⭐⭐⭐⭐

#### 当前问题
- 属性类型单一（只有基础数值）
- 缺少资源类属性（血量、能量等）
- 状态效果管理分散
- 难以实现复杂的属性系统

#### GC2 的设计思路（来自 Stats 系统）
- **Stats（基础属性）**
  - 攻击力、防御力、速度等基础属性
  - 只有数值，无上下限
  - 支持 Modifier 修改
  - 支持 Formula 动态计算
  
- **Attributes（动态资源）**
  - 生命值、能量值等资源属性
  - 有 MinValue 和 MaxValue（可以是 Stat）
  - 支持 StartPercent（初始百分比）
  - 自动 Clamp 到范围内
  - 提供 Ratio 计算（当前值/最大值）
  
- **StatusEffects（状态效果）**
  - 临时效果（中毒、加速、护盾等）
  - 支持持续时间和堆叠
  - 包含 OnStart、OnEnd、WhileActive 回调
  - 支持 Hidden 状态（不显示在UI）

#### 优化方向
- **实现 StatModifier 系统**
  - 已有 StatModifier 基础（参考现有计划）
  - 区分 Constant 和 Percent 修改器
  - 支持多个修饰器叠加
  
- **添加 Attribute 类型**
  - 为玩家添加 HealthAttribute
  - 支持百分比显示
  - 自动与 MaxHealth Stat 关联
  
- **实现 StatusEffect 系统**
  - 创建 StatusEffect ScriptableObject
  - 支持持续时间管理
  - 集成到技能系统（作为效果类型）
  - 提供 UI 显示支持

#### 预期收益
- ✅ 属性系统更完整（三层设计）
- ✅ 支持更复杂的游戏机制
- ✅ 资源管理更规范（Attribute）
- ✅ 状态效果统一管理
- ✅ 便于实现血条、能量条等UI

#### 应用场景
- 生命值/能量值管理
- 临时增益/减益效果
- 中毒、燃烧等持续伤害
- 护盾、无敌等特殊状态

#### 实施建议
1. 先完善 StatModifier 系统
2. 添加 Attribute 类型支持
3. 实现 StatusEffect 基础框架
4. 集成到技能系统
5. 根据需要扩展功能

### 12. Modifier 轻量级设计 ⭐⭐⭐

**优先级**: 中  
**难度**: 低  
**收益**: 中  
**推荐指数**: ⭐⭐⭐

#### 当前状态
- 已有 StatModifier 系统初步设计
- 但实现较重（包含过多信息）

#### GC2 的设计思路（来自 Stats 系统）
- **Modifier 结构体**
  - 极度轻量：只包含 StatID 和 Value
  - 作为 struct（值类型）避免分配
  - 无时间、来源等额外信息
  
- **ModifierList 管理类**
  - 维护 List<Modifier> 和缓存的总值
  - 添加/移除时更新缓存
  - O(1) 获取总修改值
  
- **Modifiers 容器**
  - 分别管理 Constant 和 Percent 两个 ModifierList
  - 计算公式：`(base + constant) * (1 + percent)`
  - 简单高效

#### 优化方向
- **简化 Modifier 结构**
  - 移除 Source、Duration 等信息
  - 这些信息由外部系统管理
  - Modifier 只负责数值修改
  
- **使用 struct 而非 class**
  - 减少GC压力
  - 提升性能
  
- **分离关注点**
  - Modifier：纯数据
  - ModifierList：集合管理
  - StatModifierEffect：生命周期管理

#### 预期收益
- ✅ 性能提升（更少的内存分配）
- ✅ 代码更简洁
- ✅ 职责更清晰
- ✅ 易于理解和维护

#### 实施建议
1. 重构现有 StatModifier 为轻量级结构
2. 创建 ModifierList 管理类
3. 在外部系统管理时间和来源信息
4. 充分测试性能改进

### 14. Memory Token 存档系统 ⭐⭐⭐

**优先级**: 中  
**难度**: 中  
**收益**: 中  
**推荐指数**: ⭐⭐⭐

#### 当前问题
- 缺少统一的存档系统
- 状态序列化分散在各处
- 难以实现完整的存读档功能

#### GC2 的设计思路（来自 Stats 系统）
- **Token 模式**
  - Token：轻量级数据快照（纯数据）
  - Memory：定义如何创建和恢复 Token
  - 分离存档数据和运行时对象
  
- **分层 Token 设计**
  - TokenTraits 包含 TokenStats、TokenAttributes、TokenStatusEffects
  - 每个子系统管理自己的 Token
  - 组合而非继承
  
- **统一接口**
  - `GetToken(target)`：创建快照
  - `OnRemember(target, token)`：恢复状态
  - 与 GC2 的 Save 系统集成

#### 优化方向
- **创建 Token 基础框架**
  - PlayerToken：玩家状态快照
  - EnemyToken：敌人状态快照
  - SkillToken：技能状态快照
  
- **实现 Memory 系统**
  - PlayerMemory
  - EnemyMemory
  - SkillMemory
  
- **集成到存档系统**
  - 统一的存档接口
  - 支持多存档槽
  - 自动/手动存档

#### 预期收益
- ✅ 统一的存档架构
- ✅ 易于扩展新存档内容
- ✅ 分离数据和逻辑
- ✅ 便于实现存档相关功能

#### 应用场景
- 游戏存档/读档
- 关卡重试（快照恢复）
- 回放系统
- 调试工具（状态保存）

#### 实施建议
1. 创建 Token 和 Memory 基类
2. 为核心系统实现 Token
3. 实现基础存读档功能
4. 逐步扩展到所有系统
5. 根据需要添加压缩/加密
